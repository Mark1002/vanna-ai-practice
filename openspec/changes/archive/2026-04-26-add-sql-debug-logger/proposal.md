## Why

While developing and demoing the Vanna agent, we have no easy way to see the SQL the LLM produced for each user question. Inspecting it currently means reading UI components or attaching a debugger. A lightweight terminal print of every generated SQL statement would make the natural-language → SQL behavior immediately visible during local development.

## What Changes

- Add a `TerminalSqlAuditLogger` that subclasses Vanna's `AuditLogger` and prints the SQL string for each `run_sql` tool invocation to stdout.
- Wire the logger into the `Agent` constructor in `main.py` via the existing `audit_logger` extensibility point.
- Filter to `tool_name == "run_sql"` only — other tool invocations (visualize, memory) are not logged to keep the terminal output focused.
- Include `conversation_id` and `request_id` in each log line so multiple concurrent sessions can be disambiguated.
- No-op for non-`run_sql` events; no other tool invocations are silently muted elsewhere.

## Capabilities

### New Capabilities
- `sql-debug-logging`: Prints the SQL string generated by the LLM to the terminal each time the `run_sql` tool is invoked, for local development and debugging.

## Impact

- **Code**: `main.py` (wires the new logger into `Agent`); one new module containing the `TerminalSqlAuditLogger` class.
- **Dependencies**: None added; uses `vanna.core.audit.AuditLogger` and `vanna.core.audit.models.ToolInvocationEvent` already shipped with Vanna.
- **Runtime**: One extra `print` per `run_sql` invocation. Negligible cost. Output goes to stdout only — no files, no network.
- **Privacy**: SQL strings may include literal values from the user's question. Acceptable for local debugging against the bundled `Chinook.sqlite`; this logger is not intended for production environments handling sensitive data.
